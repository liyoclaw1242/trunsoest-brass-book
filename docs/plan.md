# 原型二 執行計畫

目標是一個完整度比原型一高的可玩版本：有場景物件、有村民、有輸贏，能從頭玩到結局。做完之後再跑幾輪優化。

## 這一版要驗證什麼

1. 規則能指向一類物件或單一物件，並改變它能不能被使用、進入、取走、破壞。
2. 物件被破壞後，依賴它的機制跟著改變（廣播器壞了，該區不再公示）。
3. 保護物件的條文本身也要公示，對聽到的角色才生效。
4. 重置撕掉保護條文後，物件重新變得可以破壞。
5. 玩家一眼看得出物件的狀態：完好、受規則保護、損壞。
6. 「聽不聽這條廣播」是不是一個真正的抉擇。
7. 村民取代單一怪物後，壓力夠不夠、看不看得懂。
8. 誘導村民有沒有實際用處。

第 1 到 4 點的邏輯已在引擎測試中通過，這一版要讓它們在畫面上也成立。

## 第一階段：做出來

每個里程碑完成的條件寫在「驗收」。做完一個再做下一個。

### M0 環境確認

- 跑 `npm test`，確認 Node 與 Blender 版本，確認 Blender 能無介面執行一支最小的 bpy 腳本並匯出 glb。
- 讀完文件後提出實作計畫：技術選擇（建議 Vite＋npm 安裝的 three）、每個里程碑怎麼驗證、你看到的風險。
- **驗收**：回報上述內容，停下來等使用者確認。

### M1 Blender 場景

- 依 `docs/scene-spec.md` 寫每類物件的 bpy 腳本和 `build_scene.py`，產出 `public/village.glb` 和 `public/scene.json`。
- 寫 `tools/validate-scene.js`，檢查 `scene.json` 每筆都有 `id`、`type`、`state`、`verbs`，id 不重複，動詞都在 `VERBS` 裡，`owner` 和 `parent` 指得到東西。
- 用 Blender 從正上方和斜上方各算一張圖，存進 `docs/playtest/m1/`。
- **驗收**：驗證腳本通過；兩張圖裡十二類物件互相分得出來（自己打開圖確認）；佈局符合規格的「村子的佈局要求」。

### M2 畫面骨架

- three.js 載入 `village.glb`，正交鏡頭斜俯視，鏡頭跟著外鄉人。
- 用節點名稱對應 `scene.json` 的 id，隱藏 `__col`，依狀態顯示對應的子物件。
- 外鄉人在格子上移動（WASD），碰撞來自 `__col` 和引擎的 `attempt`。
- E 互動：靠近物件時顯示它支援的動詞，E 是第一個，數字鍵選其他的。
- **驗收**：能走遍整個村子；能對每一類物件執行它的動詞；`object` 事件會切換模型狀態。附截圖。

### M3 規則書與公示

- 筆記面板：`world.notes('outsider')`，只有認知到的條文顯示內容，其餘只顯示有幾條沒聽過。顯示生效數量和上限。
- 廣播：完好廣播器的範圍圈、目前正在唸的條文、唸完的進度。玩家要看得出自己在不在範圍內、離開範圍要走多遠。
- 「受規則保護」的外框，用 `world.protectedBy(id, 'outsider')`。
- 重置時全畫面顯示「以上規則無效」，被撕掉的條文在筆記裡劃掉。
- 設計者視角開關：顯示所有條文、每條的漏洞（`hole`）、每個角色認知到哪些條文。
- 違規、衝突、村民拒絕行動都要有畫面回饋。
- **驗收**：照 `engine/engine.test.js` 的流程在畫面上手動或用腳本重現一次，每一步都看得出發生了什麼。附截圖。

### M4 村民

- 先在引擎加上村民需要的邏輯並補測試，再接畫面。
- 行為：平時在自己家附近走動；認知到抓捕令就追外鄉人；絕不違反自己認知到的規則；不離開影響範圍。
- 三種同化程度的行為差異依 `docs/design.md`。
- 誘導：對半同化的村民按 E，至少提供「請他邀請我進屋」和「請他去拿信物」。
- 喚醒：聽不到廣播 30 秒降一級，收到自己的信物降一級。
- 玩家要看得出每個村民的同化程度，以及他是不是在追自己。
- **驗收**：引擎測試涵蓋「村民拒絕違規」「村民在邊界停下」「喚醒」；畫面上兩種誘導都做得到。

### M5 輸贏

- 影響範圍、界石、走出範圍即勝利。書被搬動時範圍跟著移動。
- 被抓到送回中心、同化度加 1；安靜處消退；到 3 就輸。
- 第三次重置代表書活過來，判輸。
- 開始畫面和結局畫面，結局畫面列出：用時、書寫了幾條、重置幾次、喚醒了幾個村民。
- 50 秒沒有新條文時書自己動筆。
- **驗收**：三種結局都能實際達成。

### M6 整合試玩

- 寫 `tools/playtest.js`（建議用 Playwright）：自動操作外鄉人跑完一局，輸出事件紀錄、規則書紀錄和關鍵時刻的截圖。
- 至少寫兩條不同的通關路線（例如「砸廣播器裝聾」和「誘導村民搬書」），確認都走得通。
- 人工檢查一次：有沒有什麼都不做就贏的方法，有沒有無解的死局。
- **驗收**：兩條路線的紀錄和截圖存進 `docs/playtest/m6/`；`npm test` 通過；更新 `CLAUDE.md` 的指令區。

## 第二階段：優化回合

最多三輪。每一輪：

1. **準備材料**：跑試玩腳本，把事件紀錄、規則書紀錄、截圖存進 `docs/playtest/round-N/`，再加一份 `HOW_TO_RUN.md`（怎麼啟動、怎麼跑腳本）。
2. **請評論員看**：呼叫 `playtest-critic` 子代理。只告訴它這是第幾輪、材料在哪個資料夾。不要告訴它你覺得哪裡好、哪裡有問題。
3. **分類它的意見**：
   - 不觸及已定案設計、改動小：這一輪就改。
   - 屬於「這一版先採用的預設」的數值或做法：可以改，在 changelog 說明。
   - 觸及已定案設計，或需要新機制：寫進 `docs/open-questions.md`，不改。
   - 你不同意的：在 changelog 寫下不採納的理由。
4. **改完重新驗證**：`npm test`、重跑試玩腳本、確認沒有把別的弄壞。
5. **記錄**：在 `docs/changelog.md` 寫這一輪 critic 的每一項意見和處理結果，commit。

提前結束的條件：critic 沒有提出高嚴重度的問題，或同一個問題連續兩輪都修不掉（寫進 open-questions）。

## 結束時的總結

用使用者讀得懂的方式回報，不要貼紀錄檔：

- 這一版能做什麼，怎麼啟動。
- 八個驗證目標各自的結果：成立、不成立、還無法判斷，各附一句依據。
- 每一輪 critic 說了什麼，你怎麼處理。
- `docs/open-questions.md` 裡等使用者決定的問題。
- 你自己沒驗證到的部分。
