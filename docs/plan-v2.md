# 改版計畫 v2

設計在原型二之後有大幅更新（見 `docs/design.md` v2）。這一輪要依新設計重新實現遊戲。能沿用的就沿用，不合新設計的就重寫，由你盤點後決定。

## 和上一版最大的差別

1. **書有了自己的時鐘**：活性量表，隨時間和玩家的行為上升，到頂就輸。
2. **規則用抽的**：每一類行為有一池候選條文，分三級，權重隨活性改變。亂數可指定種子。
3. **勞動經濟**：村民工作供養書，決定它能維持幾條規則、活性漲多快。喚醒村民等於罷工。
4. **條文類型隨階段改變**：限制 → 義務 → 定義。
5. **同化度改成 0 到 5**，加入「舒適的誘惑」：接受好處有實際效益，也讓你更接近被轉化。
6. **六種結局**：被轉化、逃跑、四種封印。
7. **循環的開場**：村子是上一次放逐的結果。

## 這一版要驗證什麼

1. 機率讓書像一個有狀態的對手，而不是讓玩家覺得只是運氣不好。前期抽到嚴謹條文時，玩家來得及反應。
2. 玩家看得懂兩個時鐘：同化度管得了，活性停不了。
3. 玩家看得出勞動流向書，並且看得出喚醒村民會讓書變弱。
4. 舒適的誘惑真的有吸引力，而且玩家事後會發現代價。
5. 逃跑在前期做不到，中後期出現窗口，越後期越短。
6. 定義類條文造成「大家都當你是市民，但你不能聽到那句話」的局面。
7. 每一種封印都做得到，而且各自的代價在結局畫面上看得出來。
8. 上一版已驗證的東西沒有壞：規則指向物件、公示才生效、重置後恢復可破壞。

## 階段

### R0 盤點

- 讀 `docs/SUMMARY.md`、`docs/changelog.md`、`docs/open-questions.md`，確認上一版實際做到哪裡。
- 把舊的 `docs/design.md` 改名為 `docs/design-v1.md`，放入新的三份文件，更新 `CLAUDE.md` 的「先讀」清單。
- 列出：哪些程式可以沿用、哪些要改、哪些要重寫，以及理由。寫進 changelog。
- 上一版 `open-questions.md` 裡標「已暫定」的項目，若和新設計衝突，以新設計為準並註記。
- **驗收**：盤點結果和這一輪的實作計畫。

### R1 引擎

全部是純邏輯，放 `engine/`，用 node 測試。

- 可指定種子的亂數產生器，引擎內所有隨機都經過它。
- 活性：時間、學習、倒退、階段判定、到頂。
- 候選條文池：依 `docs/rule-pools.md` 建資料，照寫條文的原則擴充；依類別和等級權重抽選；階段解鎖義務類與定義類。
- 擴充條文時用 `write-rules` skill；每擴充完一類，請一個沒寫那批條文的子代理用 `audit-rules` skill 審查，處理完高、中嚴重度的問題再往下。
- 寫 `tools/validate-rules.js` 做機械檢查：`key` 不重複、動詞都在 `VERBS`、`target` 指得到 `scene.json` 裡存在的類型或物件、每條都有 `hole`、每一類三個等級都有。掛進 `npm test`。
- 發現漏洞的機率、書寫時間（寫完才排入廣播）。
- 勞動：工作狀態、勞動比例、可維持的規則數、超過時最舊的褪色。
- 同化度 0 到 5、舒適項目與下限、安靜處消退。
- 定義類條文的兩種效果（村民把你當市民；你認知到就判輸）。
- 傳染。
- 六種結局的判定。
- **驗收**：每一項都有測試。另外加兩個統計測試：固定種子下抽一千次，三級的比例在各活性下符合權重；同一個種子跑兩次，規則書寫出的內容完全相同。

### R2 場景

- 用 Blender 腳本新增物件：工作站（紙坊、墨坊）、山羊、繩子、隕石魔法書、戶籍冊、山羊鈴鐺、刻字石，以及村外的「荒野深處」區域。圖書館要明確存在，書放在裡面。
- 更新 `scene.json`、驗證腳本和佈局檢查。
- 入口附近放上一次放逐的痕跡。
- **驗收**：驗證腳本通過；俯視圖裡新物件分得出來；從村子到荒野深處有路可走。

### R3 畫面與介面

- 活性量表與目前階段。階段改變時要有明顯提示。
- 書寫中的提示：正在寫、寫了多久。筆跡依等級不同。
- 同化度、持有的舒適項目、每一項的好處與代價。
- 村民的工作看得見：生產、把東西送進圖書館。追人的村民和工作的村民要分得出來。
- 可維持的規則數下降、條文褪色時的回饋。
- 設計者視角加上：這條的等級、當時的抽選權重、種子。
- **驗收**：用固定種子的腳本截圖，每一項都看得到。

### R4 村民與經濟

- 工作循環、被動員追人時離開工作、喚醒後罷工。
- 提供舒適的互動：村民主動提出，玩家可以接受或拒絕，之後可以放棄。
- 傳染、喚醒、最老的村民（搬運者）只能用山羊鈴鐺喚醒。
- 山羊：不受任何規則約束，會亂走、會吃公告牌的紙，用繩子繫住後可以引著走、可以馱書。
- **驗收**：引擎測試涵蓋；畫面上喚醒三個村民後，活性上升速度和可維持的規則數明顯下降。

### R5 結局

- 六種結局的觸發與結局畫面。畫面列出：用時、種子、書寫了幾條、重置幾次、活性最高到多少、每個村民的下場（留下、離開、喚醒、死亡）。不加評語。
- 開始畫面交代最少的背景，並可輸入種子。
- **驗收**：六種結局各用一支固定種子的腳本實際達成。損毀結局若因條件太嚴而做不到，說明卡在哪裡。

### R6 整合試玩與平衡

- 試玩腳本涵蓋六種結局。
- 檢查：什麼都不做，大約幾分鐘後輸；全程躲在聽不到的地方會怎樣；前期硬闖邊界會怎樣；有沒有單一必勝策略；有沒有無解的種子（跑二十個種子看）。
- **驗收**：結果寫進 `docs/playtest/r6/` 和 changelog。

### 優化回合

流程同上一版（準備材料、請 `playtest-critic` 看、分類意見、改完重驗、記錄），最多三輪。這一輪請評論員特別看：

- 機率公不公平：玩家輸的時候，覺得是自己的決定造成的，還是骰子造成的。
- 兩個時鐘看不看得懂。
- 舒適的誘惑是不是真的讓人想拿。
- 每種結局的代價有沒有傳達到。

`.claude/agents/playtest-critic.md` 的「從這幾個角度找問題」請加上這四點。

每個優化回合開始前，先對整個條文池跑一次 `audit-rules`。

## 工作規則（同上一版，另加）

- 所有隨機都要經過可指定種子的亂數產生器。任何測試或試玩腳本都要寫明種子。
- 條文是這個遊戲的核心內容。新增或修改條文時，照 `docs/rule-pools.md` 的原則寫，並列在 changelog。
- 數值是起點。調整時記錄調整前後的值和原因。

## 結束時的總結

寫進 `docs/SUMMARY-v2.md`：

- 怎麼啟動，推薦先試哪幾個種子。
- 八個驗證目標各自的結果：成立、不成立、還無法判斷，各附一句依據。
- 六種結局各自做不做得到。
- 你調過哪些數值。
- 每一輪評論員說了什麼，你怎麼處理。
- 等使用者決定的問題，以及你沒驗證到的部分。
