# 寫條文

你在替黃銅書代筆。遊戲裡的書目前不是由語言模型即時驅動，它寫得出什麼，完全取決於條文池。這份流程要確保每一條都讓玩家讀得懂、引擎判得出來，而且留有出路。

## 開始前先讀

- `docs/design.md` 的「書的本性」和「這一版先採用的預設」。
- `docs/rule-pools.md` 的現有條文，避免重複。
- 引擎的 `VERBS`，以及 `scene.json` 裡有哪些物件類型。

## 兩種入口

- **一類行為**：玩家做了什麼，例如「躲進水井」。直接從步驟 1 開始。
- **一個物件**：例如「山羊」。先列出玩家會拿它做的兩三件事，每件事各自當成一類行為，再從步驟 1 開始。

## 步驟

1. **想清楚書的動機**。它想阻止什麼？它在保護什麼？寫下這條規則會洩露什麼（它在乎什麼、東西在哪）。
2. **選反應類型**：保護資產、管制物品、補定義、給村民加義務、給村民開豁免。對象若是它管不到的（動物、天氣），只能繞路去約束人。
3. **寫一條鏈，不要只寫一條**：粗糙、普通、嚴謹各一。較嚴的那條，就是把較鬆那條最容易被鑽的漏洞補上後的樣子。
4. **填欄位**：

   | 欄位 | 內容 |
   |---|---|
   | `key` | 唯一名稱，英文小寫加連字號 |
   | `text` | 條文 |
   | `tier` | 粗糙、普通、嚴謹 |
   | `category` | 行動、藏身、資產與公示、自保、村民 |
   | `stage` | 限制、義務、定義 |
   | `who` | any、citizen、outsider |
   | `verb`、`target`、`cond`、`mode` | 同引擎的定義 |
   | `hole` | 漏洞。嚴謹條文填系統層面的出路 |
   | `trigger` | 玩家的什麼行為會讓書考慮寫這一類 |
   | `leaks` | 這條洩露了什麼，沒有就留空 |

5. **寫 `text`**：
   - 一句話，盡量不超過 25 個字。
   - 法條口吻，客氣有禮。書真心認為自己是善意的。
   - 不解釋理由，不用括號補充。
   - 沒打算限制的欄位就不要寫進去，那正是漏洞的來源。

## 每一條都要過的檢查

- **判得出來**：動詞在 `VERBS` 裡，玩家做得出來，而且能用 `who`、`verb`、`target`、`cond` 表達。表達不了就改寫，或在 changelog 提出要新增的動詞。
- **漏洞讀得出來**：粗糙至少兩個、普通剛好一個，而且只看條文文字就想得到，不需要亂試。
- **嚴謹條文有出路**：至少寫明一種，例如不聽到它、製造矛盾、等重置、它也綁住村民、讓不受約束的對象代勞、定義不清。
- **對村民的影響**：這條也約束村民時，他們的生活受什麼影響？如果苛待了村民，書會需要一條豁免，請一併寫出來。豁免也佔額度。
- **衝突**：和憲法或現有條文衝突時，標註「會觸發裁決」。這是特色，不是錯誤。
- **不造成死局**：這條生效後，`docs/design.md` 的六種結局至少還有兩種做得到。
- **不重複**：不是池裡某一條換個說法。

## 例子：水井

| 等級 | 條文 | 漏洞或出路 |
|---|---|---|
| 粗糙 | 外鄉人不得藏身於井中。 | 別處能藏；站在井裡但沒有「藏」算不算 |
| 普通 | 任何存在不得進入水井。 | 村民沒辦法打水，書得補一條「市民取水不在此限」，而你可以說自己在取水 |
| 嚴謹 | 水井僅供市民取水，取水以外的進入一律禁止。 | 已喚醒的村民還算不算市民沒有定義；請村民替你下去 |

## 完成後

1. 更新 `docs/rule-pools.md` 的表格和引擎的條文資料。
2. 在 `docs/changelog.md` 列出新增的條文。
3. 跑條文驗證腳本和 `npm test`。
4. 請另一個沒寫這批條文的代理用 `audit-rules` 審查。

## 不要做的事

- 不要寫沒有出路的條文。
- 不要一次替同一類寫超過六條。先審過再加。
- 不要為了湊數而寫。寧可少。
- 不要改動 `docs/design.md` 的已定案內容。
